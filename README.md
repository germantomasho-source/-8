# NEW YEAR SECRET ROULETTE 🎄 — этапы 1–2: комнаты, рулетка, распределение

Что есть: создание комнаты, код из 5 символов, ссылка-приглашение, вход по коду/ссылке, имена,
список участников в реальном времени (2–30), закрытие набора организатором, переподключение.
**Этап 2:** кнопка «Начать розыгрыш» (только организатор, только когда все в сети), распределение на сервере
(алгоритм Саттоло + `crypto.randomInt`), общий отсчёт 5…1 и синхронная рулетка по серверному времени, личная карточка
результата (конфетти, звук). Результаты хранятся только на сервере и переживают обновление страницы, обрыв и перезапуск.

## Запуск
    npm install
    npm start            # http://localhost:3000
    npm test             # 45 тестов: протокол (10), соединения (8), розыгрыш (13), браузер/Playwright (6+8, пропускаются без Playwright)

Переменные: `PORT` (3000), `DATA_FILE` (data/rooms.json), `TRUST_PROXY=1` (за прокси/хостингом).
Тайминги розыгрыша: `COUNTDOWN_MS` (5000), `SPIN_MS` (9000), `COUNTDOWN_LEAD_MS` (1500), `DONE_TTL_MS` (30 суток для готовых комнат).
Настройки для тестов: `CREATE_LIMIT` (20 комнат/час с одного IP), `HEARTBEAT_MS` (20000), `ROOM_TTL_MS` (сутки), `CLEANUP_MS` (10 мин), `NYSR_TEST=1` (включает /__stats).

## Проверка с телефонов
- В одной Wi-Fi сети: откройте `http://<IP-компьютера>:3000` на телефонах.
- Через интернет: `npx cloudflared tunnel --url http://localhost:3000` (или ngrok) даст https-ссылку.

## Публичный хостинг (Render и аналоги)
Нужен постоянный Node-процесс с WebSocket. Залейте папку в GitHub-репозиторий → Render → New Web Service
(`render.yaml` уже есть). Для сохранения комнат при перезапуске нужен persistent disk
(`DATA_FILE=/data/rooms.json`); без диска файл стирается при каждом деплое.

## Структура
- `server/server.js` — HTTP + WebSocket, логика комнат (сервер — источник истины, токены игроков не рассылаются).
- `server/store.js` — хранилище (память + JSON). Заменяемо на Redis без изменения протокола.
- `public/index.html` — клиент (оригинальный дизайн сохранён).
- `test/` — rooms (протокол), connections (замена/обрыв/мёртвые сокеты/утечки), ui (браузер), helpers.

## Протокол (JSON по WebSocket `/ws`)
Клиент → сервер: `peek`, `create{name}`, `join{code,name|token}`, `setclosed{closed}`, `leave`, `ping`.
Сервер → клиент: `peek`, `joined{code,token,you}`, `room{room,you}`, `left`, `error{code,msg}`, `hb`.

## Протокол этапа 2
Клиент → сервер: `startdraw` (организатор), `sync{c}` (замер времени).
Сервер → клиент: `room` теперь содержит `now` и `room.draw = {countdownAt, spinStart, spinEnd}` (только время, без распределения);
`result{targetId,target,jitter}` — отправляется ТОЛЬКО самому участнику (при старте и при каждом входе по токену); `sync{c,s}`;
`left{kept:true}` — выход после старта (место и результат сохраняются). Ошибки: `offline{names}`, `too_few`, `started`, `not_host`, `storage`.
Полное распределение (`room.draw.assign`) лежит только в `data/rooms.json` на сервере и ни в одно сообщение не попадает.

## Что важно знать
- Клиент получает свой результат сразу при старте (рулетка должна знать, где остановиться) и показывает его только после остановки колеса; свой результат пользователь теоретически может увидеть в DevTools, чужие — нет.
- Статус «в сети» определяется по WebSocket + heartbeat (до ~40 с задержки при внезапной потере связи телефона).
- Без persistent disk на хостинге `data/rooms.json` стирается при деплое — результаты тоже.
